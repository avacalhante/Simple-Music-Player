LISTENING ANALYTICS — HOW THE METRICS ARE MEASURED
===================================================

Everything below lives in `analytics.db`, a Room database that is separate
from `songs.db` (the library). Nothing here touches the library schema.
Writes are posted to a single-thread executor ("AnalyticsExecutor"), so the
player thread never waits on SQLite and the recorded event order is stable.

Reading this file: [source] names the class or file, [table] names a table.


1. RAW EVENTS
-------------

play_start  [table]
  One row per track start. Written when playback actually starts: either a
  media item transition while the player is already playing, or
  onIsPlayingChanged(true) after starting/pressing play (see
  `AnalyticsRecorder.onTrackStart`). Preparing or restoring the queue while
  paused also fires a transition, but does not write a play. Pausing and
  resuming one track keeps the same attempt.

    track_id        MediaStore id of the track (NOT the library Room row id)
    playlist_id     all-tracks playlist id when the browse root was the
                    tracks root, otherwise 0 (unknown)
    source          browse root at the time: all_tracks, playlist, folder,
                    artist, album, genre, or "unknown"
    started_at      epoch seconds
    start_position_seconds
                    how far into the track playback began. Non-zero when a
                    saved queue position was resumed, so listening time and
                    quick skips are measured from here, not from 0.
    duration_seconds  starts at 0 and is back-filled once the player
                    reports a duration (the media metadata does not carry
                    one in Media3 1.11.1)
    session_id      the listening session this play belongs to (0 when the
                    play is not attributable to a session)

play_end  [table]
  One row per attempt that ended. Written by `AnalyticsRecorder.onTrackEnd`,
  which is called from three places:

    1. Player.onPositionDiscontinuity when the media id changed. Media3
       dispatches this BEFORE onMediaItemTransition, so oldPosition.positionMs
       is still the outgoing track's real position. A seek inside the same
       track has the same media id and does not end the attempt.
    2. Player.onMediaItemTransition with reason REPEAT (a restarted track
       is a new attempt).
    3. PlaybackService shutdown, using the player's current position.

    ended_at        epoch seconds
    position_at_end how far the track got, in seconds
    fully_played    1 when position >= duration - 3 seconds
    skipped         1 when not fully played (the complement of fully_played)
    quick_skip      1 when skipped and only <= 15 seconds were listened to
                    (position_at_end - start_position_seconds)


2. THRESHOLDS (defaults picked by judgement, not by measurement)
----------------------------------------------------------------

  quick skip window              15 seconds   [ListeningAnalytics]
  end-of-track leeway             3 seconds   [AnalyticsRecorder]
  repeat window                  10 minutes   [ListeningAnalytics]
  "not played recently"          90 days      [ListeningAnalytics]
  session gap                     5 minutes   [ListeningAnalytics]
  recent session rows shown         5         [StatsActivity]
  weekly top rows shown             5         [StatsActivity]
  most played rows shown            20        [StatsActivity]
  rows sampled for aggregation      500        [StatsActivity]
  artist/album/genre rows shown      5        [StatsActivity]
  days shown                          14        [StatsActivity]
  library ids resolved per chunk    400        [StatsActivity]


3. THE SCREEN (StatsActivity, main menu -> "Listening stats")
------------------------------------------------------------

SUMMARY

  Total plays              COUNT(play_start)
  Total listening time     SUM over play_end of
                           MAX(0, MIN(position_at_end, duration_seconds)
                                  - start_position_seconds)
                           when the duration is known, otherwise
                           MAX(0, position_at_end - start_position_seconds).
                           [PlayEndDao.getTotalListenedSeconds]
                           Start position is subtracted so resuming a saved
                           position does not count the part played earlier.
                           Plays that never ended have no play_end row, so
                           they contribute nothing: paused or abandoned time
                           is never counted as listening.
  Finished tracks          fully_played * 100 / end_count (integer division)
  Skipped tracks           100 - finished, because the two are complements
  Never played             (distinct library media_store_ids)
                             - (distinct track_id in play_start)
                           [SongsDao.getDistinctTracksCount,
                            PlayStartDao.getDistinctTrackCount]

  Rates are 0% when there is no play_end row yet.

TOP 5 THIS WEEK / SOUNDTRACK OF THE MONTH

  Both are plain play counts inside a local-time period
  [PlayStartDao.getMostPlayedTrackIdsInPeriod]:

    SELECT track_id, COUNT(*) AS play_count FROM play_start
    WHERE started_at >= :since AND started_at < :until
    GROUP BY track_id ORDER BY play_count DESC LIMIT :limit

  week   local midnight of the locale's first day of week
         (Calendar.firstDayOfWeek: Sunday in en-US, Monday elsewhere)
         to the same moment 7 days later
  month  local midnight of the 1st to the same moment next month
  [StatsActivity.getWeekBounds / getMonthBounds]

  The section titles carry the period: "Top 5 this week (25 Oct – 31 Oct)"
  and "Soundtrack of October", with month and day names from
  DateFormatSymbols in the device locale.

  Weekly rows    top 5 tracks of the week, ranked 1..5, play count on the
                 right. The rank is only shown for this list.
  Monthly rows   the single most played track of the month, with its count.

  Titles are resolved against the library like the most played lists, so a
  play of a track that no longer exists is dropped and can leave the weekly
  list shorter than 5. Ties on play count have no defined order.

  Periods are computed from "now" every time the screen opens, so the
  numbers restart on the first day of the week/month rather than
  accumulating. A section is hidden while its period has no plays yet
  (e.g. early on the first day of a month).

MOST PLAYED TRACKS / ARTISTS / ALBUMS / GENRES

  Query:  SELECT track_id, COUNT(*) GROUP BY track_id
          ORDER BY play_count DESC LIMIT 500
  The 500 ids are resolved against the library in chunks of 400 (SQLite's
  bind-parameter limit is close to that), ids for tracks that no longer
  exist are dropped, then:
    tracks    -> first 20, ranked
    artists   -> grouped in memory by track.artist, sum of play counts,
                 top 5, blank names skipped
    albums    -> same, grouped by track.album
    genres    -> same, grouped by track.genre
  Aggregation happens in memory rather than in SQL because the playback
  side records no artist/album/genre keys; joining them to the library is
  a read of rows we already resolved.

AVERAGE LISTENING HOURS BY WEEKDAY

  One row per weekday that has at least one closed session, in `%w` order
  (Sunday first). Averaged over that weekday's closed sessions:

    start_minutes = local minute-of-day of the session start
                    (hour * 60 + minute, 0 .. 1439)
    length_seconds = the same session length as above, clamping included

  Both are plain AVG()s. The row shows "start – start + length", each side
  rounded to the nearest minute, so a Tuesday whose sessions average a
  20:36 start and 3:54 of listening reads "Tuesday 20:36 – 20:40".
  [ListeningSessionDao.getWeekdaySessionWindows]

  The end is therefore the mean start plus the mean length, not the mean
  of the session end times. For the same weekday all sessions usually
  start in a similar band, so the two are close.

  Caveats:
    * The start is an arithmetic mean of minutes since midnight, so a
      weekday with sessions on both sides of midnight would average
      towards midday. Rare, and not corrected.
    * A session ending after midnight wraps: a 23:30 start with 2 hours
      shows 01:30 as the end.
    * A weekday with a single session shows that one session's window.
      Rows become meaningful as history accumulates.
    * Sessions with no recorded length (the interrupted-play case below)
      pull the average down instead of being dropped.

PLAYS BY DAY OF WEEK

  day of week CAST(strftime('%w', started_at,'unixepoch','localtime') AS INT)
              0 = Sunday .. 6 = Saturday
  GROUP BY the bucket, ordered by play count descending, so the busiest
  weekday comes first. Only weekdays with plays are shown. This counts
  plays; the section above averages whole sessions.

NOT PLAYED RECENTLY  ("forgotten favorites")

  SELECT track_id, MAX(started_at) AS last_played_at FROM play_start
  GROUP BY track_id
  HAVING MAX(started_at) < now - 90 days
  ORDER BY last_played_at ASC LIMIT 20

  The cutoff is applied to the grouped maximum, not with a WHERE clause:
  filtering rows first would still list a track that was played recently
  just because it also has an old play. Oldest first; the trailing value
  on each row is that date. Section is hidden when nothing has ever been
  played, and shows its empty text when everything played is recent.

LISTENING SESSIONS / RECENT SESSIONS

  A session is a stretch of continuous listening. There is no in-memory session
  state: every play start asks the store for the open session
  [ListeningAnalyticsStore.resumeOpenSession], which is the single writer of
  listening_sessions, so a process death or an app restart cannot disagree with
  it.

    * an open session whose last activity is within 5 minutes -> the play joins it
    * an open session whose last activity is older            -> it is closed at
      that last activity, and a new session is opened at this play's started_at

  "Last activity" is a persisted fact, not a timestamp kept in memory:

    COALESCE(play_end.ended_at,                       -- the play ended
             play_start.started_at + duration,        -- it never ended, but its
                                                         duration is known
             play_start.started_at,                   -- neither is known
             session.started_at)                      -- no plays at all
    maximized over the session's plays
  [ListeningSessionDao.getOpenSessionState]

  So every play start restarts the 5 minute window, and so does every play end:
  a 9 minute track followed by a 3 minute pause resumes the session, while the
  same track followed by a 6 minute pause starts a new one.

  Nothing closes a session eagerly. Playback stopping (service shutdown) and the
  app being killed only end the current play. The session stays open until the
  window has passed, which is why closing the app and reopening it a minute
  later continues the same session instead of adding a near-empty one.

  A stale session is closed at the two points where it can be noticed:

    * the next play start, via resumeOpenSession (see above)
    * a stats screen load, via ListeningAnalyticsStore.closeStaleSessions, so
      the last session of the day is shown without waiting for more playback

  Closing sets listening_sessions.ended_at (a closed-marker only) to that last
  activity, not to "now", so a late sweep cannot lengthen a session. The close
  is idempotent (`WHERE ended_at = 0`), so two closers can never move it.

  Session length is NOT taken from ended_at - started_at, because that would
  count idle time between the last track and the moment the session was
  noticed to be over. It is derived from the plays instead [ListeningSessionDao]:

    last_activity = MAX over the session's plays of
                      COALESCE(play_end.ended_at,
                               play_start.started_at + play_start.duration_seconds)
    length = MIN(last_activity, ended_at) - started_at

  The COALESCE fallback covers a play that never ended (the process went
  away mid-track): its start plus its known duration is the best estimate of
  how far it got. The outer MIN clamps the result to the moment the session
  was closed, so an interrupted last play cannot make this session run into
  the next one. Paused time between two plays is therefore excluded, and a
  pause longer than the gap ends the session at the last play, not at the
  resume.

  Sessions                  COUNT of closed sessions (open ones excluded)
  Average session length    sum(length) / count (integer division)
  Longest session           max(length)
  Average tracks per session  sum(track_count) / count, one decimal
  Sessions with one song    sessions with exactly one play * 100 / count

  Recent sessions lists the 5 newest closed sessions, newest first:
  label = local start time, value = length + play count.


LISTENING TIME BY DAY

  bucket   strftime('%Y-%m-%d', started_at,'unixepoch','localtime')
  value    SUM of MAX(0, position_at_end - start_position_seconds) for the
           ended plays started that day
  Newest day first, last 14 days. Local timezone, so it matches how you
  think of a listening day. Plays that never ended are left out.

                            average position_at_end / duration_seconds,
                            i.e. the songs you habitually stop early.

                            10 minutes of its previous play.

                            there is no UTC variant.

  getMostPlayedTrackIdsInPeriod / getMostPlayedTracksInPeriod   backing the
                            two period summaries above.
  getMostPlayedTrackIdOnDate   most played track of a single date.

                            discovery helpers.


5. CAVEATS
----------

  * Attribution is best-effort. The service knows the last browse root it
    was asked for, not which playlist you opened a track from, so source is
    "unknown" for playback started from widgets, notifications, search or a
    track screen, and playlist_id is 0 in those cases.
  * duration_seconds stays 0 when the player never reports a duration. Such
    a play can never be marked fully_played.
  * Counts survive library changes: play counts keep counting for tracks
    that were deleted, but the lists drop rows whose track is gone.
  * Percentages use integer division, so a rate can round down.
  * Sessions only split on a gap between two different plays. Pausing one
    track for longer than the gap and resuming it does not end the session,
    because no new play_start row is written and resuming is not an event the
    analytics layer sees. Sessions from before this
    feature have session_id 0 and are not counted.
  * A session interrupted by a crash stays open until the 5 minute window has
    passed, so it is not shown until then - up to a 5 minute delay after
    playback stops, and longer if nothing happens to notice it.
  * A session's close marker is written once. A row closed by an older build
    that had already overwritten it keeps its shortened length.
  * Data never leaves the device. There is no analytics network call; the
    only way data leaves the app is the user-initiated export below.


6. BACKUP, RESTORE AND CLEARING
-------------------------------

  Export stats (stats screen overflow menu) writes the three tables, with
  their ids, into one json file through the system file picker [AnalyticsBackup].
  The file carries a version marker that the importer checks.

  Import stats REPLACES the whole history with the file's content, it does not
  merge: two histories would have colliding ids. Ids are kept as they are, so
  every play still points at its session and its end row. A file without the
  current version marker is rejected, and the replace is confirmed first.

  Clear stats deletes the three tables in one transaction, after a confirmation.

  Both replace and clear can run while a track is playing, which takes the
  current play's row away. Play ends are therefore written with
  `INSERT ... SELECT ... WHERE EXISTS (play_start)`
  [PlayEndDao.insertForExistingPlay], so a cleared history cannot leave an end
  row behind that would still be counted by the engagement numbers.

If a threshold changes, it changes in one place: `ListeningAnalytics` for
the storage-side constants and `StatsActivity` for the display limits.
